# 09-提交信息规范

> 本规范基于 [Conventional Commits 1.0.0](https://www.conventionalcommits.org/zh-hans/v1.0.0/) 并结合项目 DDD
> 分层架构定制，所有提交必须遵循。

## 一、提交信息格式

```
<type>(<scope>): <subject>

<body>

<footer>
```

### 1.1 格式约束

- ✅ **Header 行必须**：`<type>(<scope>): <subject>`
- ✅ **Body 可选**：解释"为什么"而非"做了什么"，每行不超过 72 字符
- ✅ **Footer 可选**：用于标注破坏性变更 `BREAKING CHANGE:` 或关联 Issue
- ❌ 禁止仅写 `init`、`update`、`fix`、`123` 等无语义信息
- ❌ 禁止在提交信息开头包含 BOM 字符（`﻿`）
- ❌ 禁止使用 HEREDOC 在 PowerShell 中传递提交信息（PowerShell 不支持），改用多个 `-m` 参数

### 1.2 Header 行约束

- 整行不超过 **72 字符**（中文按 2 字符计）
- `<subject>` 首字母不大写，结尾不加句号
- `<subject>` 使用祈使语气（如"新增"而非"新增了"）
- 中文项目允许 `<subject>` 使用中文，`<type>` 和 `<scope>` 使用英文

## 二、Type 类型定义

| Type       | 含义     | 使用场景                                                     |
|------------|----------|--------------------------------------------------------------|
| `feat`     | 新功能   | 新增业务能力、新增 API 接口、新增领域服务                    |
| `fix`      | 缺陷修复 | 修复 bug、修复测试失败、修复编译错误                         |
| `refactor` | 重构     | 不改变外部行为的代码结构调整，如重命名、提取方法、调整包结构 |
| `perf`     | 性能优化 | 提升性能但不改变功能，如优化 SQL、减少内存分配               |
| `docs`     | 文档变更 | 新增或修改文档、注释、README、规范文件                       |
| `test`     | 测试相关 | 新增测试、修复测试、补充测试覆盖                             |
| `build`    | 构建系统 | 修改 pom.xml、依赖版本、构建脚本、CI 配置                    |
| `ci`       | 持续集成 | 修改 CI/CD 配置、流水线脚本                                  |
| `chore`    | 杂项     | 不属于上述类型的琐碎变更，如更新 .gitignore、清理临时文件    |
| `style`    | 代码风格 | 格式化、缩进、空格调整，不影响代码逻辑                       |
| `revert`   | 回退     | 回退某次提交                                                 |

### 2.1 Type 选择原则

- ❌ 禁止用 `chore` 代替 `feat`/`fix`/`refactor`（有明确语义时必须用对应 type）
- ❌ 禁止用 `update` 作为 type（这不是 Conventional Commits 类型）
- ✅ 同时涉及多个类型时，选择 **最主要**的变更类型

## 四、Subject 书写规范

### 4.1 语言

- ✅ 优先使用 **中文**描述（与项目沟通语言一致）
- ✅ 英文模块名、技术术语保持原文（如 `QLExpress4`、`MapStruct`、`@HttpExchange`）

### 4.2 语气与措辞

- ✅ 使用祈使语气：`新增`、`修复`、`重构`、`移除`、`补充`、`优化`
- ❌ 禁止使用过去时：`新增了`、`修复了`、`重构了`
- ❌ 禁止使用被动语态：`被修改`、`被删除`

### 4.3 示例对照

| ✅ 正确                                                                  | ❌ 错误                                        | 问题                          |
|--------------------------------------------------------------------------|------------------------------------------------|-------------------------------|
| `feat(kernel): 新增 QLExpress4 条件求值网关实现`                         | `update version, add QLExpress4`               | 无 type、无 scope、非祈使语气 |
| `fix(shared-domain): 修复 Entity.equals() 类型安全问题`                  | `fix entity equals bug`                        | 无 scope、描述过于笼统        |
| `refactor(core-domain): 重构聚合根包结构 aggregateroot → aggregate/root` | `123`                                          | 完全无语义                    |
| `chore(rules): 启用规则文件 alwaysApply 配置`                            | `update skills alwaysApply from false to ture` | 无 type、无 scope、拼写错误   |
| `docs(file-service): 补充 file-service-parse-engine 规划文档`            | `add docs`                                     | 无 scope、描述笼统            |

## 五、Body 书写规范

### 5.1 何时需要 Body

- ✅ 提交涉及 **多个文件**或 **多个变更点**时必须写 Body
- ✅ 提交涉及 **架构调整**或 **破坏性变更**时必须写 Body 说明原因
- ❌ 简单的单文件修改（如修正拼写）可省略 Body

### 5.2 Body 格式

```
feat(kernel): 新增 QLExpress4 条件求值网关实现

1. 在 core-infrastructure 新增 QlExpressConditionEvaluationGateway
2. 通过 @ConditionalOnProperty 控制实现切换
3. 保留原有 SpelConditionEvaluationGateway 作为默认实现
4. 新增 12 个单元测试覆盖表达式求值场景
```

### 5.3 Body 约束

- ✅ 每行不超过 72 字符
- ✅ 使用有序列表说明变更要点
- ✅ 解释"为什么"做这个变更，而非"做了什么"（代码 diff 已说明 what）
- ❌ 禁止在 Body 中粘贴大段代码

## 六、Footer 书写规范

### 6.1 破坏性变更

```
feat(api): 重构 ApprovalFlowApi 接口签名

将 PageInfo<T> 替换为 PageData<T> 以对齐全局分页规范

BREAKING CHANGE: ApprovalFlowApi.list 返回类型由 PageInfo<ApprovalFlowResponse> 改为 PageData<ApprovalFlowResponse>
```

### 6.2 关联 Issue

```
fix(approval-infrastructure): 修复审批实例级联删除遗漏审批记录

Closes #42
```

## 七、特殊场景规范

### 7.1 多类型混合提交

当一次提交涉及多种类型时，按以下优先级选择 type：

1. `feat` > `fix` > `refactor` > `perf` > `docs` > `test` > `build` > `chore`
2. 在 Body 中说明其他类型的变更

```
refactor(shared-exception): 重构异常体系并补充单元测试

1. BaseException 改为 abstract，构造函数改为 protected
2. 子类覆盖链式方法，协变返回具体类型
3. 修正 UNKNOW_ERROR 拼写为 UNKNOWN_ERROR
4. 新增 67 个单元测试覆盖异常类契约
```

### 7.2 大范围重构

```
refactor(shared): 规范化错误码体系并补齐公共基础模块单元测试

1. 错误码规范化：统一为 5 位纯数字格式，划分通用/公共基础/业务核心/业务服务码段
2. shared-exception 基础异常类重构：BaseException 改为 abstract
3. 公共基础模块 bug 修复：Entity.equals() 增加 getClass() 校验
4. shared-types ID 校验补齐
5. 新增 560 个单元测试覆盖上述修改
```

### 7.3 文档与代码混合

```
docs(rules): 新增 09-提交信息规范并补充错误码规范

1. 新增 .trae/rules/09-提交信息规范.md
2. 更新 08-错误码规范.md 补充 HTTP 状态码映射
3. 移除错误消息中的 {} 占位符
```

## 八、禁止示例

| ❌ 错误示例                         | 问题                      | ✅ 正确写法                                     |
|-------------------------------------|---------------------------|-------------------------------------------------|
| `init`                              | 无 type、无 scope、无语义 | `chore: 初始化项目结构与开发规范`               |
| `123`                               | 完全无语义                | `refactor(core-domain): 重构聚合根包结构`       |
| `update`                            | 非法 type                 | `refactor(xxx): 重构 xxx 模块`                  |
| `fix bug`                           | 无 scope、描述笼统        | `fix(file-domain): 修复 Excel 解析表头丢失问题` |
| `Update README`                     | 无 type、首字母大写       | `docs: 更新 README 使用说明`                    |
| `feat:add user`                     | type 后无空格、scope 缺失 | `feat(approval-domain): 新增用户审批能力`       |
| `feat(approval): Add user approval` | subject 首字母大写        | `feat(approval-domain): 新增用户审批能力`       |

## 九、提交前检查清单

提交前必须确认：

- [ ] Header 行格式为 `<type>(<scope>): <subject>`
- [ ] type 是合法类型（feat/fix/refactor/perf/docs/test/build/ci/chore/style/revert）
- [ ] scope 是本文档定义的合法 scope
- [ ] subject 使用祈使语气，无句号结尾
- [ ] Header 行不超过 72 字符
- [ ] 无 BOM 字符
- [ ] 多文件变更已写 Body 说明
- [ ] 破坏性变更已标注 `BREAKING CHANGE:`
